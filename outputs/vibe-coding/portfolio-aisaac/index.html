01
ユーザー分析仮説検証データ分析

AIスライド生成の初回失敗を 13.4% → 5.1% に。仮説から検証まで自分で回した改善。

13.4% → 5.1%初回生成failure率（改善後 約20h・14,000+セッションで検証）
Background / 背景
ユーザーの声(VoC)を追う中で、「AIスライド生成の最初の入力でAIが応答を生成できず、そのまま離脱する」ユーザーが一定数いることを確認。初回体験が定着に直結していた。
Hypothesis / 仮説
失敗率を下げれば → 満足度が上がり → retentionが向上するはずだ。
Approach / アプローチ
約3万件を分析し、失敗原因を3つのroute（聞き返し／不適切な拒否／空応答）に分類。優先度を共有し、緊急バグはエンジニアへ、残りは企画メンバーと議論。分析基盤はAIで自作。
Result / 結果
初回失敗を 13.4% → 5.1%（route別すべて改善）。定性的にも失敗入力の大半が正常処理へ。retention改善の土台をつくった（満足度・retentionへの影響は継続trackingが次の対象）。
Learning / 学び
分析要件の定義から改善後の検証までを主導した経験。
02
課題定義オーナーシップUXリサーチ進行中

「なぜ企画が通らないのか」を突き止め、UXリサーチを自ら立ち上げた。

Background / 背景
PMとして企画を出しても通らないことがあり、理由を掘るとデータ・明確なユーザー仮説・説得力が足りていなかった。根本は「チームがユーザーを深く理解できていない」こと。
Hypothesis / 仮説
良い企画の前提は“正確なユーザー理解”。体系的に理解する仕組みをつくれば、企画の精度も説得力も上がる。
Approach / アプローチ
1on1で課題を提起 → チームも共感し、データの多い韓国ユーザーをまず見る方向に整列。4つの問い（誰を／課題は何か／解決できているか／どう解決すべきか）を軸に、インタビュー設計・定性分析のフレームワークを整備。
Result / 結果
現在進行中。これは指示ではなく、自分が必要だと感じて立ち上げた取り組みで、問題定義からチームを動かすところまでを自分で行った。
Learning / 学び
課題は与えられるものではなく、自分で定義してチームを動かせるものだと実感した。
03
AIネイティブ自動化PythonLLM評価

LLM品質評価のQAパイプラインをAIで自作。そして「LLMでLLMを評価する」難しさに向き合った。

Background / 背景
LLMプロダクトは出力が確率的なため、毎回結果が変わる。手動QAでは、幻覚や文脈忘れの再現率把握・優先度づけに限界があった。
Hypothesis / 仮説
API経由の自動化 + LLM評価を入れれば、間欠的な問題を“再現確率(%)”として数値化し、検証を大量・反復で回せる。
Approach / アプローチ
Pythonで自社プロダクトのAPIを直接呼び出してスライドを自動生成し（必要に応じて「25枚に修正」などのマルチターン要求も自動化）、生成物(JSON)を外部LLMに渡してPASS/FAILを判定。判定は2層で設計——構造・数値はルールで（Rule-based）、幻覚・言語混在などの中身はLLMが読んで（LLM-based）チェックする。これらをすべてAIで自作した。
Result / 結果
パイプラインは構築できたが、実運用までは至らなかった。理由は「LLMでLLMを評価する」判定精度を十分に担保できなかったこと。判定のブレが自動QAの信頼性の壁になった。
Learning / 学び
①企画者でもAIで検証ツールを自作できる実行力を得た。②「自動化・LLM評価は万能ではなく、どこまで信頼できるかを見極めることが重要」だと身をもって学んだ。この“LLM-as-judgeの限界”の実感は、AIプロダクトに関わる上で大きな財産。
