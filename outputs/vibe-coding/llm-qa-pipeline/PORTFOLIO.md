# LLM 품질 평가 파이프라인

AI 채팅 제품의 응답 품질을, 사람이 매번 눈으로 보지 않고 **자동으로 대량·반복 검증**하기 위해 만든 도구입니다. 기획자가 직접 만들었습니다.

## 왜 만들었나

LLM 제품은 출력이 확률적입니다. 같은 입력에도 결과가 달라집니다. 그래서 수동 QA로는 두 가지를 할 수 없었습니다.

- **간헐적으로만 나는 문제**(환각, 문맥 망각)의 재현율을 알 수 없다
- 그래서 무엇을 먼저 고쳐야 하는지 우선순위를 못 세운다

가설은 이랬습니다. 자동화 + LLM 판정을 넣으면 이 문제들을 **"재현 확률 %"라는 수치로 바꿀 수 있고**, 그러면 우선순위가 나온다.

## 어떻게 만들었나

```
테스트 케이스 생성 → 제품 API 자동 호출 → 생성물(JSON) 수집 → 2층 판정 → 리포트
                        (멀티턴 수정 요청 포함)
```

**판정을 두 층으로 나눈 것**이 핵심입니다. 하나로 하면 어느 쪽도 제대로 못 합니다.

| 층 | 무엇을 보나 | 왜 이 방식인가 |
|---|---|---|
| 규칙 기반 (`rule_validator.py`) | 구조·개수·필수 필드·수치 범위 | 기계적으로 판정되는 건 LLM에 맡길 이유가 없다. 싸고 결과가 흔들리지 않는다 |
| LLM 기반 (`llm_validator.py`) | 환각, 언어 혼재, 요청과 응답의 적합성 | 읽어야 아는 것. 규칙으로 쓸 수 없다 |

그 외에 넣은 것들:

- **멀티턴 자동화** — "25장으로 줄여줘" 같은 후속 수정 요청까지 자동으로 이어 붙입니다. 첫 응답만 보면 실제 사용과 다릅니다
- **테스트 케이스 자동 생성** (`tc_generator.py`, `qa/tc_heuristic.py`, `qa/tc_regenerator.py`) — 손으로 쓰면 케이스가 제 편향대로 쏠립니다
- **캐시** (`core/cache_manager.py`) — 같은 입력을 다시 부르지 않게. API 비용과 시간이 실제 제약이었습니다
- **토큰 추적** — 판정 자체가 LLM 호출이라 비용이 듭니다. 얼마 드는지 모르면 돌릴 수 없습니다
- **웹 UI** (`app.py`, `templates/`, `static/`) — 결과를 팀이 보게

## 결론: 실운용까지 가지 못했습니다

파이프라인은 돌았습니다. 그런데 도입하지 않았습니다.

**"LLM으로 LLM을 평가한다"는 판정 정확도를 담보하지 못했습니다.** 같은 생성물에 대해 판정이 흔들렸고, 판정을 믿을 수 없으면 자동 QA 전체를 믿을 수 없습니다. 여기가 벽이었습니다.

되짚어보면 순서가 틀렸습니다. **사람의 판정을 먼저 쌓아 정답지를 만들고, 자동 판정이 그것과 얼마나 일치하는지로 검증해야** 했습니다. 그 정답지가 없는 상태에서 자동 판정을 먼저 만들었으니, 맞는지 확인할 방법 자체가 없었던 것입니다.

## 남은 것

- 기획자도 검증 도구를 직접 만들 수 있다는 실행력
- 그리고 **자동화의 신뢰도를 무엇으로 담보할지 정하지 않으면, 도구는 돌아도 쓰이지 않는다**는 것

## 그래서 다음에 만든 것

이 회고가 다음 도구의 설계가 됐습니다. **순서를 거꾸로 잡았습니다.**

자동 판정을 먼저 만들지 않고, **사람이 결과물을 보고 판단을 남기는 환경**을 먼저 만들었습니다. 생성 결과를 전 페이지 썸네일로 펼쳐놓고, 유저의 원래 요청과 만족도 응답을 옆에 붙여, 팀이 같은 화면을 보면서 **페이지 단위로** 메모를 남기면 한 곳에 모이게 했습니다.

여기서 두 가지를 의도적으로 다르게 했습니다.

**① 평가 항목을 미리 정하지 않았습니다.** 처음엔 평가 카테고리를 13개 만들어 체크박스로 붙였다가 전부 지우고 자유 메모만 남겼습니다. 기준을 먼저 박아두면 팀이 그 칸에 맞는 것만 보게 되고, 그 13개는 제가 혼자 상상한 목록이라 맞다는 근거가 없었기 때문입니다. 실제 문제가 그 밖에 있으면 영영 안 보입니다.

**② 판정 단위를 쪼갰습니다.** 결과물 하나가 아니라 그 안의 한 페이지가 단위입니다. "이 결과물이 나쁘다"는 고칠 수 없지만 "3페이지에서 소제목이 줄바꿈된다"는 고칠 수 있습니다.

계획한 순서는 이렇습니다.

```
① 사람이 실물을 보고 판단을 남긴다        ← 지금 여기
② 쌓인 메모에서 반복되는 축을 뽑아 기준을 만든다
③ 그 기준을 자동 판정으로 옮긴다
```

②에서 반드시 재야 하는 게 **평가자 간 일치율**입니다. 같은 페이지를 두 사람이 봤을 때 판정이 얼마나 겹치는가. 여기가 낮으면 기준이 덜 여문 것이고, 그 상태로 ③에 가면 안 됩니다. 사람끼리도 합의가 안 되는 기준을 자동화하면 판단이 아니라 잡음을 자동화하는 셈입니다.

이게 이 파이프라인에서 빠져 있던 부분입니다. ③을 먼저 만들었으니 ①②가 없었고, 그래서 판정이 맞는지 확인할 방법이 없었습니다.

**현재 ①까지입니다.** 도구는 팀에 공유했고 평가는 이제 쌓이기 시작했습니다. ②③은 아직 안 했습니다.
